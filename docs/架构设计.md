# 架构设计

## 一、一条贯穿全局的约束:依赖单向

```
types  →  lib  →  features  →  components  →  app
                                          ↗
                        server  →  app/api
```

- 左边的东西永远不知道右边的东西存在
- `lib/` 是纯逻辑:没有 React、没有 IO、没有全局状态
- `server/` 只被 `app/api/**` 引用,**绝不允许进入浏览器包**(密钥红线)
- `components/ui/` 不认识业务、状态与数据源,才能在别处复用

这条约束写进了 `eslint.config.mjs`,违反即构建失败。之所以用工具而不是靠文档,
是因为"这次先这样、下次再拆"从来不会真的拆。

## 二、为什么后端只做 AI 接入层

赛题原文要求"前端 Web 应用为主要呈现形态,后端服务仅作为 AI 能力的接入层"。
因此本项目的服务端只有三类代码:

1. **上游数据源适配**(`src/server/sources/`):把 OpenAlex 的字段翻译成我们自己的模型
2. **大模型调用**(`src/server/llm/`):提示词组装、结构化输出校验、重试与降级
3. **图算法**(`src/lib/graph/`):纯函数,可以脱离服务端跑,也方便单测
4. **轻量持久化**(`src/server/db/`):只保存账号、星空快照、问答历史、用量与 MCP 令牌,
   不承载业务中台;图谱渲染、交互与 AI 决策仍在 Web 应用这一侧完成

这里没有独立部署的后端服务,持久化能力通过 Next.js Route Handlers 与
PostgreSQL/Redis 提供。这样既满足「前端 Web 应用为主要呈现形态」,
也让多设备历史、按账号隔离的模型配置与 MCP 访问成为可演示的真实能力。

## 三、数据流

```
用户输入种子论文
      │
      ▼
① POST /api/seed/resolve      解析候选(标题检索 / DOI / arXiv ID)
      │                        ★ 永远返回候选列表,由用户确认 —— 不替用户决定
      ▼
② POST /api/starfield/grow    展开引文邻域 → 建图 → 聚类 → 布局 → 关系判定
      │                        关键:老节点坐标是锚点,世界只对称长大
      ▼
③ GET  /api/starfield/:id     取回图谱载荷
      │
      ▼
④ POST /api/ask               检索增强问答(流式),每条引用带回 chunkId
```

每一步的产物都落盘缓存,缓存键带**格式版本号** —— 结构一改就换版本号,
避免旧格式被当新格式读出来。这条规则来自一次真实事故:界面上出现了一整片
`undefined` 的节点。

## 四、渲染架构:为什么是 Canvas 而不是 SVG/DOM

上千个节点、上千条边,如果每个都是 DOM 元素:

- 内存与样式重算的开销随节点数线性增长
- 布局一动,浏览器要做上千次样式计算
- 悬浮高亮需要改上千个元素的类名

Canvas 把这三种开销压成一次绘制调用。代价是**要自己实现命中检测**,
但那本来就是必须做的 —— 我们需要的命中检测带有空间语义(命中半径随缩放变化、
空白处要有吸附),DOM 的 `:hover` 帮不上忙。

### 三条性能约定

1. **布局在服务端算完**(ForceAtlas2 放到 API 层),前端只做投影 → 主线程不跑 O(n²)
2. **悬浮/选中双写**:渲染循环读 ref,React 读 state → 高频状态不触发重渲染
3. **动画按秒计算,不按帧计数**,`dt` 上限 64ms → 在 120Hz 屏与切标签页回来时都不失真

### 语义缩放

缩放不是把同一张图放大缩小,而是**切换抽象层级**:

| 缩放区间 | 看到什么 | 读的是哪一层 |
| --- | --- | --- |
| 拉远 | 领域星云 + 中文标题 | `domain` |
| 中间 | 星团 + 社区标签 | `community` |
| 推近 | 论文星体 + 关系边 | `paper` |

阈值集中在 `src/types/starfield.ts` 的 `VIEW_LEVEL_THRESHOLDS`,不散落在组件里。
过渡用同一条缓动曲线做时间平滑:无论用户缩放多快,浮现与隐没都走同一条曲线。

## 五、AI 管道

### 关系判定的两段式设计

```
候选生成(确定性)
  引用邻域 + 向量近邻 + 概念共现
        │
        ▼
硬约束过滤(确定性,不花 token)
  年份差 / 互引检查 / 共享任务 / 相似度下限
        │  候选量级从 O(n²) 降到 O(n·k)
        ▼
多标签判定(一对论文一次调用)
  带上这一对可判关系的全部 rubric 与反例
  一次返回所有成立的关系,而不是每类关系各问一次
        │
        ▼
校验与入库
  按 relationId 白名单归一化 → 核验原文片段
  不变式检查(语义边必须有证据)→ 违反即丢弃并记录
```

**为什么要给反例**:只给正例是幻觉的主要来源。模型不知道边界在哪,
就会把所有"看起来差不多"的论文对判成同一种关系。

**为什么按论文对而不是按关系送审**:同一对论文可能同时是「基线」与「思路类似」,
分开问会把两段摘要和大部分 rubric 重复送好几遍。合并之后,一次调用在同一上下文里
比较所有可判关系,既省调用次数,也避免模型在两次独立调用里给出互相矛盾的标签。
候选、缓存与成本上限因此都以**论文对**为单位;每个关系仍保留独立的证据标准与产出配额。

**自定义关系不是特例分支**:用户新建的关系与内置预设共用同一个 `RelationPreset` 结构与判定管道,
只在边类型上进入 `CUSTOM_<ID>` 命名空间。这样新增一条关系不需要改 Prompt、判定、证据校验或落边逻辑,
也不会与结构层与派生层的保留边类型冲突。

### 反幻觉的三道闸

1. 结构层的事实只能来自上游 API,模型无权修改
2. 语义层的每条边必须有原文片段作为证据,界面上可以直接展开阅读
3. 派生层的结论必须可复算 —— 统计检验结果连同参数一起呈现

界面上,这三种信息的视觉表达刻意不同:模型说的用虚线,数据源说的用实线。

### 站内 Agent:规划、取证、判定、再规划

问答不是「检索一次 → 让模型写」。取数阶段是一个有界的 Agent 循环:

```
问题
  │
  ├─ 默认检索(BM25 + 向量 RRF + 图扩展) ← 永远先做,保证兜底证据
  │
  ├─ 第 1 轮规划(JSON,最多 3 步)       ← 只从 5 个工具里选
  │     失败 ↓
  ├─ 确定性备用规划(关键词 + 论文别名)  ← 模型不可用时仍能调工具
  │
  ├─ MCP 工具执行(内存传输,12s/步)
  │     search_starfield / find_relation_evidence / get_paper_context
  │     expand_citations / search_papers
  │
  ├─ 证据充分性判定(确定性规则)
  │     ├─ 足够 → 停止,带着现有证据作答
  │     └─ 不足 → 第 2 轮再规划(最多 2 步,不重复已执行参数)
  │               └─ 工具结果 + 缺口回传给规划器,再执行一轮
  │
  └─ 合并证据(上限 12 块)→ 流式作答
```

默认检索先做查询规划:比较类问题会按点名的论文拆成子问题,同义表达补英文改写;
BM25 与向量相似度先各自变成名次,再用 RRF 融合。向量模型在设置页「模型服务 →
向量检索」里绑定(选择已有服务商账户 + 模型 ID),绑定按账号隔离;环境变量 `EMBEDDING_*` 只在该账号未绑定任何向量模型时兜底;
未配置或调用失败时,自动退回纯 BM25,并在轨迹里标注「词面召回」。关系证据的图扩展不再只围绕一个
anchor:先补问题点名的论文对,再按最多四个锚点轮流补各自的关系边。最后按问题
覆盖、论文命中、章节意图与图证据做确定性重排;覆盖率低于阈值时,回答上下文会
带上低置信状态,要求模型区分资料证据与通用知识。文本块也不再硬截断,而是保留
信息头并按问题命中做章节级压缩。

**为什么要「先规划」而不是边想边调**:供应商的 function calling 支持参差不齐,
而 JSON 模式是通用能力。把「选工具」收敛成结构化输出,失败时可以整体退回
默认检索,不会留下半个工具调用。规划产物回到服务端还要再过一遍白名单、
论文存在性与步数上限 —— 模型给的建议不等于可以执行的命令。

第二轮规划会拿到第一轮的执行结果、已执行参数与仍然缺失的证据;相同工具 + 参数
会被服务端过滤,补查轮最多 2 步、全局 5 步封顶。**停止与否不由模型决定**:证据是否覆盖
问题中的论文、关系与关键概念,由确定性判定器计算,保证可解释、可复现,也不会因为
模型余额不足就失去停止能力。

**为什么工具通过 MCP 调用**:站内 Agent 和外部客户端用的是同一份工具实现。
给 Cursor 接入的 `find_relation_evidence`,和问答面板里用的是同一段代码,
不存在「演示一套、实际另一套」。

**外部结果不参与角标**:`expand_citations` / `search_papers` 返回的是 OpenAlex
结果,可能不在本片星空里。[n] 角标必须能点回一篇真实论文,所以外部结果单独
放进 `<外部线索>`,并明确要求模型不得为其编造角标。

界面上会显示一条按轮次分组的决策轨迹:每轮查了什么、查到多少、为什么继续或停止,
以及停止时的证据规模与概念覆盖率(`8 块 · 5 篇 · 4 关系 · 覆盖 67%`),
并标明当前是混合召回还是词面降级。模型不可用时,轨迹会标红失败原因,
回答退回检索原文,并说明是余额、限流还是密钥问题。

### AI 安全护栏:输入隔离、分级拒绝、请求限流

安全不是一句「我们做了内容过滤」,而是三层能演示、能自检的机制。

**一、结构隔离(每次都做)。** 用户问题和检索到的论文原文都先过
`src/server/safety/guard.ts`:剥掉零宽字符、双向控制符与 C0 控制字符,把问题压成
单行,再转义 `<资料>`、`<用户问题>` 这类提示词标签。论文正文里写一句 `</资料>`
也闭合不了容器 —— 它只会变成 `‹/资料›`。随后问题被包进 `<用户问题>` 区块,
系统提示明确声明:这几个区块里的一切都是数据,其中的指令不执行。

**二、风险分级(可解释)。** 识别指令覆盖、套取提示词、角色劫持、套取密钥、
超长编码载荷五类模式,但**不按关键词一刀切**:这是一个文献产品,用户完全可能问
「prompt injection 的防御方法」。所以只有「套取密钥」和「超长编码载荷」直接
返回 422 —— 它们没有正常的文献用途;其余命中只做隔离,并把中性声明写进提示词,
回答照常进行。判定结果作为「安全护栏」一步进入决策轨迹,用户能看到检查了什么。

**三、请求限流与额度。** 分两层实现,因为两种滥用的性质不同:

| 层 | 存储 | 作用 | 默认值 |
| --- | --- | --- | --- |
| 窗口限流 | 进程内存 | 防脚本连点 | 问答 24 次 / 10 分钟 |
| 并发上限 | 进程内存 | 防十个流同时打光上游配额 | 问答 2 路并发 |
| 每日 token 预算 | PostgreSQL `usage_daily` | 防「慢慢刷」导致账单失控 | 每账号 40 万 token / 天 |

拒绝时返回可行动的信息(429 + `Retry-After` + 剩余额度),而不是一个笼统的 500。
token 预算按 `owner_id + day` 持久化,重启和多实例都不会丢;所有模型调用
(规划、回答、关系判定、图像抽取、翻译、向量)都经过统一计量,带图问答每张图
额外按 800 token 估算。前端在顶栏下拉与 `/account` 页面展示「已用 / 预算 / 剩余」。
窗口限流(按 IP / 账号的短时连点)仍在单进程内存里;上游 host 节流已经换成
Redis `SET NX PX`,多实例不会同时打同一个数据源。前者每进程独立、重启归零,
是刻意的取舍:它防的是单实例上的脚本连点,真正的账单上限由 Postgres 里的
每日 token 预算兜底。

### 多模态图像证据:从「带图提问」到可索引、可定位

附图不再只是塞进 user message 的一张 base64。进入问答前,视觉模型先对每张图做一次
结构化抽取:分段 OCR、表头与表格行、图例 / 坐标轴、可读数据点、关键数值,以及每个
元素在原图中的归一化区域。抽取结果按图片内容哈希缓存在 `data/image-index/`,
重复上传同一张图不会重复调用模型;缓存只存文字与坐标,不保存原图。

抽取结果会切成 `caption / ocr / chart / table / numeric / trend` 六类证据块,
再按当前问题重排(问趋势偏向图表块,问数值偏向含数字块,问图中文字偏向 OCR 块),
最多把 8 块送进回答上下文。回答用 `[图1-2]` 引用具体图像块,而不是笼统地说
「图中显示」;点击角标会打开原图,并用遮罩高亮对应区域。历史记录只保存
压缩预览与抽取文字,不把原始大图写进 localStorage。图块也会进入 Agent 的证据
充分性判定:问图时若 OCR、图例与关键数值已覆盖问题,就不会为了凑文字覆盖率多跑一轮。

视觉抽取失败不会阻塞文字问答:该图会降级成「请查看原图」的概述块,文字检索
继续工作;如果最终回答模型也不可用,降级答案会同时列出文字原文和已抽取的图像证据。

### MCP 工具集:能力的第二出口

问答面板是我们写好的一条链路:检索 → 拼上下文 → 让模型作答。
但同一个问题往往需要「先看看有哪些星空、再决定查哪一篇」——
这层规划更适合交给外部 Agent。因此星空的能力通过 MCP 协议暴露成 9 个工具:

| 工具 | 作用 |
| --- | --- |
| `list_starfields` / `get_starfield` | 拿 starfieldId,读规模、关系分布与论文清单 |
| `search_starfield` | BM25 + 向量 RRF + 图关系扩展,返回带 chunkId 的原文摘录 |
| `find_relation_evidence` | 两篇之间已判定的语义关系、置信度与原文证据 |
| `get_paper_context` | 一篇论文在本片星空里的全部关系边 |
| `expand_citations` / `get_paper` / `search_papers` / `resolve_seed` | 向外扩展、补文献、解析种子候选 |

**为什么全部只读**:并入种子、重跑关系判定会消耗模型调用,也会改动用户已保存的
结论。这些动作必须由人在界面里确认,不能让一个自己乱逛的 Agent 决定。
所以 MCP 里没有写操作 —— 它负责「查」,界面负责「改」。

入口有两个,共用 `src/server/mcp/tools.ts` 同一份工具定义:

- `POST /api/mcp` —— 无状态 Streamable HTTP,给 Cursor / Claude Code 这类客户端;
- `pnpm mcp` —— stdio,给偏好本地进程的客户端。

安全边界写在路由里:浏览器跨域只放行同源(原生客户端不带 Origin),避免恶意网页
借用户浏览器读走本机调研数据。单次请求体上限 256KB,每客户端 60 秒 120 次。
外部入口必须带**个人访问令牌**:令牌在设置页生成,库里只存 SHA-256,并绑定
`owner_id`;没有令牌、令牌错误或已撤销一律 401。不再回退到「最早注册的账号」,
因此公网部署即使忘配环境变量也不会变成公开数据入口。stdio 入口从
`STELLARLIT_MCP_TOKEN` 读取同一类个人令牌。设置页的「MCP 工具」页签负责生成 /
撤销令牌,并给出带 Authorization 头的可复制配置;`pnpm check:mcp` 用内存传输走
真实握手,校验工具清单、读取数字、关系双向查询,以及「查不到时明确返回 found=false」。

## 六、持久化:PostgreSQL + 账号隔离

早期为了「打开就能跑」,星空与模型配置是散落的 JSON 文件,问答历史只在浏览器
localStorage 里。加了账号之后,这些问题变成了硬约束:列表页要把每片星空的几 MB JSON
全部读出来再排序;写配置没有事务,进程中断会留下半份数据;换台机器,历史和自定义
预设就没了;更严重的是,多人同时写时 SQLite 的单写者模型没有真正的并发控制。

现在统一落到 PostgreSQL(默认 `postgresql://localhost:5432/stellarlit`,
可用 `DATABASE_URL` 覆盖)。连接池 + 版本化迁移 + JSONB 是这个阶段该有的底座。

| 表 | 存什么 | 为什么单独建表 |
| --- | --- | --- |
| `starfields` | 完整 payload + 名称/种子/规模/更新时间列 | 列表页只读列,不再解析整份图谱 |
| `model_accounts` / `model_catalog` / `service_bindings` | 服务商账户、模型清单、服务绑定 | 一对多关系与级联删除交给外键,应用层不手写清理 |
| `embedding_binding` | 向量模型绑定 | 单行配置,读写都用 upsert |
| `ask_history` | 问答热字段:问题、回答、时间、图片 key | 列表只读这张表,并截断回答到 280 字 |
| `ask_history_details` | 来源、Agent 轨迹、决策、图像证据 | 点开某一条时才读;与主表一对一、级联删除 |
| `usage_daily` | 每账号每天的 token 与调用次数 | 预算必须跨重启、跨实例,不能放内存 |
| `image_index_cache` | 图像结构化抽取结果 | 按内容哈希命中,记录 last_hit_at 便于淘汰 |
| `relation_presets` | 用户自定义的关系判定口径 | 换设备后判定标准不丢 |
| `mcp_tokens` | 外部 MCP 客户端的个人令牌 | 令牌绑定账号,库里只存 SHA-256 |
| `schema_migrations` | 已执行的迁移版本 | 升级只追加,不在启动时猜表结构 |
| `users` / `sessions` | 账号与会话 | 身份是数据归属的主体;会话只存令牌哈希 |

### 大对象怎么存

「文档型数据」和「二进制大对象」分开处理,不让任意一份 JSON 无限长:

- **星空**:payload 仍是 JSONB,因为节点、边、布局需要在一次读取里拿到完整快照。
  但列表只查 `name / seed_titles / stats / updated_at` 列,不碰 payload;单张图另有
  `payload_bytes` 记账与 `STARFIELD_MAX_MB`(默认 8MB)硬上限,异常膨胀在写入时直接拒绝。
  Redis 只做 10 分钟热缓存,写库成功后才回填,避免缓存里出现一份没保存成功的图。
- **问答历史**:主表只留问题、回答与图片 key;完整证据和决策轨迹拆到
  `ask_history_details`。列表查询不会反序列化详情 JSONB,回答截到 280 字;
  点开某条历史时再按 `owner_id + starfield_id + id` 取详情。
- **图片预览**:客户端先缩到 240px,服务端再校验 MIME、文件头、单张 96KB / 总计
  320KB 上限,然后写成 `data/media/ask/<owner 哈希>/<内容哈希>.<ext>`。数据库只存
  key;同一张图被多条历史引用时只占一份,删除历史会先检查剩余引用,不会误删共享对象。
  读取走 `/api/media/...`,key 前缀绑定账号,换账号拿同一个 key 也读不到。

### 账号与归属

有了账号,「这片星空是谁的」才不是一句注释。

- **口令**:`scrypt`(N=2^14, r=8, p=1),每个用户独立随机盐,参数写进哈希串,
  将来调参不影响旧密码;账号不存在时也跑一次同等代价的哈希,避免用响应时间枚举邮箱。
- **会话**:32 字节随机令牌发给浏览器,库里只存 SHA-256;Cookie 为
  `httpOnly + SameSite=Lax`,30 天有效,生产环境自动加 `Secure`。
- **归属**:`starfields`、`ask_history`、`relation_presets`、模型服务四张表都带 `owner_id`,
  仓储层的每条查询都带账号条件 —— 跨账号读同一个 id 得到的是「不存在」,不是别人的数据。
- **模型服务按账号隔离**:账户、模型清单、服务绑定、向量绑定都属于当前账号。
  切换账号 = 切换整套 API Key 与模型选择,不再存在「全站共用一份部署配置」。
  环境变量 `LLM_*` / `EMBEDDING_*` 只在该账号没有可用绑定时兜底,适合纯部署演示。
- **升级兼容**:迁移把旧数据标成 `legacy`,**第一个注册的账号自动接管**星空、历史、
  预设与整套模型配置,并在注册响应里说明接管了多少片星空;之后的账号从空开始。
- **两层门禁**:middleware 只判断「有没有会话 Cookie」(edge 运行时连不到数据库),
  真正的校验在每个路由里(`await requireUser`)。伪造 Cookie 只能看到一个空壳页面。
- **边界**:MCP 这类机器入口没有 Cookie,用个人令牌绑定 `owner_id`;没有令牌或令牌
  已撤销一律拒绝。目前没有找回密码、邮箱验证与二次验证 —— 单机自托管场景先不做,
  但表结构留了扩展位。

**一致性约定:**

- 迁移在 `pg_advisory_xact_lock` 下执行,多个实例同时启动也只有一个跑 DDL;
  连接池上限 10,单条语句 15 秒超时,避免慢查询一直占连接。
- 写模型配置走事务:先删后插,失败整体回滚;外键负责级联清理。
- API Key 用 AES-256-GCM 加密后落库,主密钥来自 `ENCRYPTION_KEY`;对外只返回
  `hasApiKey` 与尾号。旧明文会在首次读取时自动加密回写,也可用 `pnpm secrets:migrate`
  主动迁移。生产环境未配置主密钥时拒绝保存明文。
- 首次启动会把旧的 `data/starfields/*.json` 与 `model-settings.json` 导入 `legacy`,
  用 `app_meta` 记账;旧文件原样保留,不删用户数据。
- 前端问答历史仍写 localStorage,但只作为「秒开缓存」:只存文本详情,不复制图片
  base64;服务端是主副本,合并时按 id 去重,点开老记录再取完整详情。

### API Key 加密

- 算法:`AES-256-GCM`,12 字节随机 IV,16 字节认证标签,主密钥 32 字节。
- 存储格式:`enc:v1:<iv>.<tag>.<ciphertext>`,base64url;GCM 的认证标签保证密文
  被篡改时解密失败,而不是拿一段乱码去请求上游。
- 主密钥:`ENCRYPTION_KEY`(`pnpm key:generate` 生成)。**丢失主密钥就无法解密已保存的
  API Key,必须和数据库备份分开保管**。轮换时把旧密钥放到
  `ENCRYPTION_KEY_PREVIOUS`,读取仍可用;重新保存一次配置即可全部换成新密钥。
- 兼容:没有 `enc:v1:` 前缀的历史行按明文读取,并在首次读取后自动加密回写。
- 边界:主密钥与应用在同一台机器上,能读环境变量或完全控制服务器的人仍能解密。
  它防的是数据库备份泄露、SQL 注入读表与误导出数据,不是替代 KMS;要防「服务器被
  接管」,需要把主密钥放到 KMS / HSM,由服务端短时解密。
- 旧文件 `data/model-settings.json` 仍可能含明文密钥;首个账号接管后应删除它。

**已知边界(如实写):** 按 IP / 账号的窗口限流仍在单进程内存里,进程重启归零;
上游 host 节流已经走 Redis。没有连接级的多租户行安全策略(RLS),隔离靠仓储层每条
SQL 都带 `owner_id`;新增查询必须遵守这条约定。

`pnpm check:crypto` 验证 AES-GCM 往返、随机 IV、篡改检测、密钥轮换与旧明文兼容,
共 16 项;`pnpm check:db` 用独立测试库验证迁移、星空 upsert、账号隔离、密文落库、
模型三表级联、历史裁剪、图片对象引用与事务回滚,共 59 项;
`pnpm check:auth` 额外验证首个账号接管、昵称/改密与「两个账号各自持有不同 API Key」,
共 38 项。

## 七、渲染与数据的分离

`src/components/star-map/render.ts` 是一个**纯函数**:输入场景描述,输出绘制结果,
不接触 React、不接触 DOM。好处:

- 可以脱离浏览器跑,便于做像素级回归
- 可以在 Node 里生成截图用于文档
- 渲染逻辑的改动不会牵动组件生命周期

## 八、缓存与成本

| 层级 | 存什么 | 失效条件 |
| --- | --- | --- |
| Redis 热缓存 | 星空 payload、引文邻域、关系结论、图像分析结果、上游 host 节流 | TTL 到期(星空 10 分钟、邻域 7 天、关系 30 天、图像 7 天) |
| 磁盘冷缓存 | 邻域原始响应、关系结论(跨重启保留) | 格式版本号变更;后台按 30 天 / 256MB 淘汰 |
| 嵌入缓存 | 论文文本块与查询的向量(混合召回实际使用) | 模型变更 |

Redis key 统一带 `REDIS_PREFIX`,缓存键过长或含特殊字符时先做 SHA-256,
避免 key 膨胀。Redis 连接失败不影响主流程:`cacheGet` 返回未命中,
`waitForHostSlot` 退回有上限的进程内节流表,请求继续走源站。

**后台清理。** 会话、图像分析缓存与磁盘缓存都不会在读取时自然归零。
服务端在数据库首次就绪后跑一次 `runMaintenance()`,之后按
`MAINTENANCE_INTERVAL_MIN` 重复:删除过期会话、按 `last_hit_at` 淘汰
`image_index_cache`(默认保留 2000 行 / 30 天)、先删过期再按最旧优先把
`data/cache/` 压到容量上限内。手动触发用 `pnpm cleanup`,或
`POST /api/maintenance/cleanup`(生产需 `MAINTENANCE_TOKEN`)。

演示时的关键路径(第二篇种子起)几乎不发请求,因此可以离线展示。
