# StellarLit 知识图谱模型

> 这份文档定义系统的**唯一数据契约**。前端的每一个视觉元素、AI 的每一次输出,
> 都必须能在这份模型里找到位置;反过来,模型里任何一条边只要落不到画面上,
> 就不该被生产出来。

---

## 一、为什么需要自己设计图谱,而不是"调 API 拿结果"

学术文献场景里存在三种完全不同性质的知识,**混在一起是绝大多数同类产品的通病**:

| 性质 | 例子 | 能不能核验 | 谁来生产 |
| --- | --- | --- | --- |
| 客观事实 | A 引用了 B | 能,上游 API 就是权威 | 数据源 |
| 语义推断 | A 是 B 的基线方法 | 不能直接核验,但能找到**原文依据** | 大模型 |
| 算法派生 | A 和 B 属于同一个研究前沿 | 能复算,过程和参数可公开 | 统计/图算法 |

如果把三者塞进同一张扁平的表,就会出现两个后果:大模型的幻觉和真实引用
看起来一样可信;而用户想核对一句话时,系统无法回答"你凭什么这么说"。

**本模型的核心决策:按「可核验程度」分层,而不是按「业务模块」分层。**
每一层有自己的生产者、自己的可信度、自己的视觉表达。

## 二、三层图谱

```
┌─ L3 派生层 Derived ──────────────────────────────────────────────┐
│  社区 Community / 领域 Domain / 潜在连接 POTENTIAL_LINK           │
│  生产者:图算法(标签传播 + 模块度、向量近邻、统计检验)            │
│  特性:全部可复算。给定同样的输入与参数,结果必然一致。            │
└──────────────────────────────▲───────────────────────────────────┘
                               │ 只读上面两层,不反过来修改它们
┌─ L2 语义层 Semantic ─────────────────────────────────────────────┐
│  基线 BASELINE_OF / 同期 CONTEMPORARY_OF / 同思路 SIMILAR_APPROACH│
│  同任务异方法 ALTERNATIVE_TO / 扩展 EXTENDS / 矛盾 CONTRADICTS     │
│  生产者:大模型 + 提示词工程                                       │
│  铁律:每条边至少携带一条 evidence,evidence 必须能指回原文        │
└──────────────────────────────▲───────────────────────────────────┘
                               │ 语义层的输入全部来自结构层,不自造数据
┌─ L1 结构层 Structural ───────────────────────────────────────────┐
│  引用 CITES / 作者 AUTHORED_BY / 发表 PUBLISHED_IN / 提及 MENTIONS │
│  生产者:OpenAlex、arXiv、Semantic Scholar                        │
│  特性:权威、可公开核验,是全系统的「事实底座」                    │
└──────────────────────────────────────────────────────────────────┘
```

**依赖方向单向**:L2 读 L1,L3 读 L1+L2;任何一层都不得反向改写下层。
这条约束由代码结构强制保证(`src/server/` 只读上游、`src/lib/graph/` 是纯函数)。

## 三、节点

节点分为**实体节点**与**聚合节点**两类。聚合节点(社区、领域)没有自己的数据,
它们是算法对实体节点的分组结果,删掉它们不影响事实层。

### 3.1 实体节点

| 类型 | 说明 | 关键属性 | 视觉对应 |
| --- | --- | --- | --- |
| `paper` | 论文 | 标题、摘要、年份、venue、引用数、DOI、字段分类 | **一颗星** |
| `author` | 作者 | 姓名、机构、ORCID | 星体的光晕(默认隐藏) |
| `venue` | 期刊/会议 | 名称、类型、CCF 等级 | 星体标签的一部分 |
| `concept` | 概念 | `kind` 细分:方法/任务/数据集/指标/主题 | 星体颜色与筛选维度 |
| `chunk` | 文本块 | 所属论文、章节、序号、向量 | **不显示**,是 RAG 检索的落点 |

`concept` 采用**统一节点 + `kind` 细分**而不是为方法/任务/数据集各建一种节点:
大模型抽取出的概念边界天然模糊(「对比学习」是方法还是主题?),强行分类只会
在数据入库时丢失信息。统一节点 + 多标签更贴近真实情况,也更容易扩展新维度。

`chunk` 是 RAG 的检索单元,它**必须携带 `locator`**(章节 / 段落序号 / 原文偏移),
否则模型给出的引用无法回溯 —— 界面上那些上标角标就会变成不可点击的装饰。

### 3.2 聚合节点

| 类型 | 说明 | 生产者 | 视觉对应 |
| --- | --- | --- | --- |
| `community` | 研究前沿(紧密的子群) | 标签传播 + 模块度最大化 | 星团 |
| `domain` | 领域(社区之上的聚合) | 层次聚类 / 字段分类 | **星云**(缩小时浮现) |
| `starfield` | 一片星空(用户的工作空间) | 用户行为 | 整个画面 |

## 四、边

### 4.1 统一结构

所有边共用一个结构,只有 `layer` 和 `evidence` 的内容不同:

```ts
interface GraphEdge {
  id: EdgeId;
  kind: EdgeKind;
  source: NodeId;
  target: NodeId;
  directed: boolean;
  layer: "structural" | "semantic" | "derived";
  weight: number;                    // 0-1,边的强度(用于布局与粗细)
  confidence: number;                // 0-1,仅语义层有意义
  evidence: Evidence[];              // 语义层:长度必须 ≥ 1
  rationale?: string;                // 语义层:模型给出的判定理由
  provenance: Provenance;            // 谁生产的、用什么参数、什么时候
}
```

### 4.2 结构层关系

| 关系 | 方向 | 来源 | 说明 |
| --- | --- | --- | --- |
| `CITES` | 有向 | OpenAlex `referenced_works` | 全系统的引力线,图谱骨架 |
| `AUTHORED_BY` | 有向 | OpenAlex `authorships` | 用于识别核心作者与团队 |
| `PUBLISHED_IN` | 有向 | OpenAlex `primary_location` | 用于会议/期刊维度筛选 |
| `MENTIONS` | 有向 | OpenAlex `topics` / 文本抽取 | 论文与概念的关联,权重=相关度 |
| `HAS_CHUNK` | 有向 | 切块管道 | 论文 → 文本块 |

### 4.3 语义层关系(参赛作品的「预设关系」)

这六类关系是**用户在设置页可维护的预设对象**,不是硬编码的枚举:

| 关系 | 方向 | 判定要点 | 硬约束 |
| --- | --- | --- | --- |
| `BASELINE_OF` | 有向 | A 是该方向公认的基线,B 以它为对照并试图超越 | 通常伴随引用 |
| `CONTEMPORARY_OF` | 无向 | 同期并行出现、解决相邻问题 | 年份差 ≤ 2,且**互不引用** |
| `SIMILAR_APPROACH` | 无向 | 核心思路同源(可能是不同任务上的同一种机制) | 允许跨领域 |
| `ALTERNATIVE_TO` | 无向 | 面向同一任务,但技术路线明显不同 | 必须有共同任务 |
| `EXTENDS` | 有向 | B 在 A 的基础上直接改进 | 必须存在引用 A→B |
| `CONTRADICTS` | 无向 | 结论相互矛盾(同条件下得到相反结果) | 必须有可对比的实验结论 |

**为什么要区分「同期但互不引用」**:这是判断"两个平行方向是否有机会合流"的关键信号,
而它恰好无法从引用图里读出来 —— 引用图只能告诉你"谁连了谁",读不出"谁本该连却没连"。

**为什么矛盾关系值得单列**:用户在文献调研里最怕的就是"读完三十篇才发现两篇结论相反"。
把矛盾显式地画成一条边,是这套图谱最有信息量的一处。

### 4.4 派生层关系

| 关系 | 方向 | 算法 | 说明 |
| --- | --- | --- | --- |
| `BELONGS_TO` | 有向 | 标签传播 + 模块度 | 论文 → 社区 |
| `PART_OF` | 有向 | 层次聚类 | 社区 → 领域 |
| `SEMANTIC_NEIGHBOR` | 无向 | 向量 kNN | 语义近邻,用于检索与"思路类似"的候选召回 |
| `POTENTIAL_LINK` | 无向 | 结构空缺 × 语义距离 | **潜在连接**:图上该连却没连的位置 |

`POTENTIAL_LINK` 是本系统的创新点,它的定义刻意做成两个正交维度:

|  | 语义距离近 | 语义距离远 |
| --- | --- | --- |
| **结构空缺高** | ✅ 真机会:该连却没连 | ⚠️ 假空缺:本来就不相关 |
| **结构空缺低** | 已成熟:继续做价值有限 | 两个独立领域 |

只有「高结构空缺 + 低语义距离」才判定成立。**这个交叉条件专门用来杀掉假阳性**:
计算机科学与法学之间跨界引用必然稀少,但这不构成研究机会。

## 五、证据链:让大模型的输出可被质询

语义层的每条边都必须携带证据。证据分五类:

| 证据类型 | 内容 | 用来支撑 |
| --- | --- | --- |
| `citation` | 上游 API 的引用记录 | BASELINE_OF / EXTENDS |
| `span` | 论文原文片段 + 定位 | 几乎全部语义关系 |
| `metadata` | 年份、venue、字段 | CONTEMPORARY_OF / ALTERNATIVE_TO |
| `embedding` | 向量相似度分数 | SIMILAR_APPROACH |
| `statistics` | 统计检验结果(Poisson 尾概率、FDR) | POTENTIAL_LINK |

一条 `span` 证据长这样:

```ts
{
  kind: "span",
  paperId: "paper:W2626778328",
  section: "introduction",
  quote: "We compare against the Transformer baseline of Vaswani et al.",
  locator: { chunkId: "chunk:W2626778328:003", start: 1240, end: 1312 },
  score: 0.92
}
```

**界面上,这段文字是可以直接展开阅读的。** 这是"反幻觉"从口号变成功能的地方:
评委点开任意一条关系,都能看到模型是读了哪句话才这么判的。

## 六、关系预设:把提示词工程变成用户可维护的对象

评分表里「Prompt 设计是否精巧」占 8%。Prompt 写在代码里等于不可维护、不可演示。
因此每类语义关系都是一个**一等公民对象**:

```ts
interface RelationPreset {
  id: string;                 // "baseline"
  label: string;              // "基线"
  labelEn: string;            // "Baseline"
  family: "lineage" | "comparison" | "conflict" | "custom"; // 只用于分组,不参与判定
  description: string;        // 一句话定义(展示给用户)
  definition: string;         // 判定标准(注入提示词的 rubric)
  negativeExamples: string;   // 反例:什么情况不算(抑制误判)
  directed: boolean;
  hardConstraints: {          // 先做确定性过滤,再交给模型 —— 省 token 且降幻觉
    requireCitation?: boolean;
    maxYearGap?: number | null;      // null = 不限
    requireSharedTask?: boolean;
    requireMutualNonCitation?: boolean;
    minSimilarity?: number | null;   // 文本相似度下限,null = 不限
  };
  visual: { tone: string; dash?: string };
  promptVersion: string;      // 判定逻辑变更时必须自增,证据链可追溯
  enabled: boolean;
  maxPerSeed: number;         // 每篇种子最多产出多少条,控制成本
}
```

**两段式判定**是这个设计的核心:

1. **硬约束过滤**(纯代码,确定性):年份差、是否互引、是否有共同任务 —— 把候选集从
   O(n²) 砍到可接受的量级,而且这一步完全不会幻觉。
2. **模型判定**(带 rubric 与反例):只在少量候选上跑,并要求给出证据片段。

这样既控住了 token 成本,也让"模型只在它擅长的地方发言"。

**一对论文一次多标签判定。** 硬约束按关系分别筛选候选,但进入模型前会先按**无序论文对**合并:
同一对论文能判的「基线」「扩展」「思路类似」挂在同一条记录下,只调用一次模型,
返回所有成立的 relationId。这样做有三个直接收益:

1. 摘要与系统约束只读一遍,调用次数从「关系数 × 候选对」降为「候选对」;
2. 多个标签在同一上下文里比较,不会出现两次独立调用对同一对论文给出互斥结论;
3. 成本上限、缓存与进度都以论文对计数,界面上的「已判定 N 对」是真实对数。

输出的可控性靠三层归一化保证:模型只能返回这一对**可判集合**里的 relationId,
未知或越界的标签直接丢弃;同一关系重复出现时只保留 confidence 最高的一条;
结果按置信度与关系清单顺序排序。没有成立关系时 `labels` 为空数组 ——
这个空结论也会缓存,避免"没有关系"的论文对每轮重复送审。

缓存键为「无序论文对 + 关系 id + 该关系的 `promptVersion`」。因此用户只改「基线」的 rubric 时,
同一对论文上「扩展」的旧结论仍然可用;另一条关系的旧结论不会被误作废。
批大小是 4 对,批间并发;整批解析失败会退回**逐对多标签**调用,兜底时不降级成单标签。

**信息架构:关系族而不是六个平铺开关。** 六条规则按用途分成三组:
谱系(基线 / 扩展)、对照(同期 / 思路类似 / 同任务异方法)、冲突(结论矛盾)。
设置页采用主从布局:左侧选关系,右侧编辑「前置条件 → 证据标准 → rubric → 产出上限」。
硬约束不再只是展示文案 —— 引用条件、年份差、共享主题、文本相似度与产出上限都可以直接调;
`null` 表示不限。`pnpm check:relations` 会校验分组、约束是否自相矛盾、版本号格式、边类型映射,
以及多标签归一化的白名单、去重、排序与空结果行为。

**自定义关系**沿用同一个预设对象,不另写一套判定代码。设置页可以从「其他」族新建:
填写中英文名称、一句话说明、方向、证据标准、判定标准与反例;id 由英文名生成并在冲突时自动加后缀,
最多 24 条。自定义边使用 `CUSTOM_<ID>` 的边类型命名空间,避免与 `CITES`、`PART_OF` 等保留类型撞名。
预设随本地覆盖一起保存,并在构建星空时作为 `presets` 覆盖发给服务端;失败的约束、产出上限与
`promptVersion` 规则与内置关系完全一致。图例、边标签、节点详情与 RAG 语料都通过同一张
「预设 → 边类型」映射还原用户写的名称,而不是显示 `CUSTOM_CAUSAL_LINK` 这样的内部值。

## 七、星空:图谱的时间维度

一次搜索换一张图,是工具;一片会长大的星空,是工作台。

```ts
interface Starfield {
  id: string;
  name: string;
  ownerId: string;
  seeds: SeedEntry[];        // 多次输入累积,记录构建顺序 —— 支撑增量构建
  createdAt: string;
  updatedAt: string;
  viewport: { x: number; y: number; scale: number };
  stats: { papers: number; edges: number; communities: number; domains: number };
}
```

### 节点的坐标是持久属性,不是布局产物

这是踩过坑才定下的规则:新增种子时,如果整张图重新布局,老星体会整体漂移
(实测中位位移可达 300px 以上),用户看到的现象就是"我一搜,原来的星图就没了"。

因此:**世界原点固定在中心,世界只做对称长大**;已有节点作为锚点被拉回原位,
新节点先插到已有邻居的重心附近再自由松弛。老星体的绝对坐标一个都不动。

社区的重新划分是另一回事:图上加了新内容,聚类结果必然变化。
处理办法是**重聚类 + 编号对齐**(按新旧社区的重叠票数做最大匹配),
让大部分论文保持原来的社区编号,只有真正被结构改变的部分才换。

## 八、不变式

这些约束在写入图之前校验,违反即拒绝入库(而不是静默降级):

1. **语义边必有证据**:`layer === "semantic"` 时 `evidence.length >= 1`
2. **结构边必有出处**:`layer === "structural"` 时 `provenance.source` 必须是上游数据源
3. **引用边不得自环**,且 `CITES` 不允许出现环(上游数据异常时丢弃该边并记录)
4. **聚合节点不承载事实**:`community` / `domain` 不得作为 `CITES` 的端点
5. **同一对节点同一关系只保留一条边**,重复判定时取 `confidence` 最高者并合并证据
6. **文本块必须有定位**:`chunk.locator` 缺失则不入库 —— 无法回溯的引用等于没有引用

## 九、与视觉编码的对应

图模型里每一种东西在画面上都有唯一对应的表达。这张表既是设计约束,也是答辩时的对照表:

| 图谱概念 | 画面表达 |
| --- | --- |
| `paper` | 一颗星,亮度与被引量相关,半径与年份相关 |
| `CITES` | 一条极细的引力线 |
| `BASELINE_OF` / `EXTENDS` | 带方向的实线,方向由流动的粒子段表达 |
| `CONTEMPORARY_OF` | 虚线(同期平行,不曾交汇) |
| `SIMILAR_APPROACH` | 冷色实线 |
| `ALTERNATIVE_TO` | 双色调的对撞线 |
| `CONTRADICTS` | **暖红色**,整张图里唯一的高饱和色 |
| `POTENTIAL_LINK` | 空缺处的暖色细环(该连却没连) |
| `community` | 星团,缩小时以标签浮现 |
| `domain` | 星云,缩小到一定程度才浮现 |
| `evidence.span` | 点击任意边后展开的原文卡片 |
| RAG 的 `chunk` 引用 | 回答里的上标角标,点击定位到星体与原文 |

**一色一义**是硬规则:暖红色全图只用于「矛盾」,暖黄色全图只用于「空缺」。
颜色一旦复用,视觉编码就失效了。
