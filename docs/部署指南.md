# StellarLit 部署指南(发布版)

面向一台全新的 Linux 服务器,从零到公网可访问。全程只用 Docker,
不需要在宿主机安装 Node、PostgreSQL 或 Redis。

---

## 一、服务器要求

| 项目 | 最低 | 建议 |
| :--- | :--- | :--- |
| 系统 | Ubuntu 22.04 / Debian 12 | Ubuntu 24.04 |
| 配置 | 2 核 4G | 2 核 4G + 2G swap |
| 磁盘 | 20G | 40G(媒体与缓存会增长) |
| 软件 | Docker 24+、Compose v2 | 最新稳定版 |

```bash
docker --version && docker compose version
```

构建阶段 Next.js 比较吃内存,2G 内存的机器务必先加 swap,否则可能被 OOM 杀掉。

```bash
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

在本地把发布提交推到远端:

```bash
git push origin main
```

```bash
git clone https://github.com/Xuezhihengg/stellarlit.git stellarlit
```

效果等价,但后续更新会麻烦一些。

## 三、配置环境变量

```bash
cp .env.docker.example .env
openssl rand -hex 24      # 输出填到 POSTGRES_PASSWORD
openssl rand -base64 32   # 输出填到 ENCRYPTION_KEY
openssl rand -hex 24      # 输出填到 MAINTENANCE_TOKEN
```

必填项只有两个:

- `POSTGRES_PASSWORD`:数据库口令,只在容器网络内使用。
- `ENCRYPTION_KEY`:必须是 32 字节(base64 或 64 位 hex)。设置页保存的厂商
  API Key 用它做 AES-256-GCM 加密。**丢失后库里已加密的密钥无法恢复。**

其余按需:

- `MAINTENANCE_TOKEN`:生产环境调用清理接口的 Bearer 令牌,不设则该接口拒绝服务。
- `SAFETY_DAILY_TOKEN_BUDGET`:每账号每日 token 预算,默认 400000。
- `APP_BIND` / `APP_PORT`:对外监听。走反向代理时改成 `APP_BIND=127.0.0.1`。

模型服务不读环境变量:LLM、向量模型、Semantic Scholar Key 全部由每个账号
登录后在「设置」里自己绑定。OpenAlex 使用账号注册邮箱。

`.env` 已被 `.gitignore` 与 `.dockerignore` 双重排除,不会进仓库也不会进镜像。

## 四、启动

```bash
docker compose up -d --build
docker compose ps
docker compose logs -f app
```

首次启动会自动建表;数据卷为空时会导入仓库自带的演示星空,标记为 `legacy`。
等待日志出现监听 3000 端口后验证:

```bash
curl -I http://127.0.0.1:3000/
```

健康检查每 30 秒请求一次首页,`docker compose ps` 里 `app` 显示 `healthy` 即正常。

### 立刻注册第一个账号

`legacy` 演示星空、问答历史与模型配置会被**第一个注册的账号**接管。
所以部署完请马上打开站点注册你自己的账号,确认后再把地址发给别人。

随后在该账号的「设置 → 模型服务」里绑定一个服务商并选择问答模型,
否则文献问答会提示未绑定模型(这是预期行为,系统不提供全局回退模型)。

## 五、反向代理与 HTTPS

### 为什么必须加一层

应用容器只监听明文 HTTP 3000 端口,它自己不做 TLS。反代负责四件事:

1. **终止 TLS**:浏览器到反代走 HTTPS,反代到容器走回环地址的明文 HTTP。
2. **收敛入口**:公网只开 80/443,3000 只绑 `127.0.0.1`,别人扫不到应用端口。
3. **传真实身份**:把客户端 IP 和原始协议告诉应用,登录 Cookie 与限流才正确。
4. **不缓冲流式响应**:问答是 SSE,反代一旦攒包,回答就会最后一次性出现。

### 前置:DNS 与防火墙

域名 A 记录指向服务器公网 IP,确认解析生效:

```bash
dig +short stellarlit.example.com
```

防火墙只放行 22/80/443:

```bash
sudo ufw allow 22/tcp && sudo ufw allow 80/tcp && sudo ufw allow 443/tcp
sudo ufw enable && sudo ufw status
```

云厂商安全组同样只开这三个端口。80 端口必须可用,ACME 签发证书要用它做验证。

### 方案 A:Caddy(推荐)

Caddy 自动申请和续期证书,自动把 HTTP 跳转到 HTTPS,并且默认就会设置
`X-Forwarded-For` 与 `X-Forwarded-Proto`,配置最少、最不容易出错。

```bash
sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https curl
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' \
  | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' \
  | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update && sudo apt install -y caddy
```

`/etc/caddy/Caddyfile`:

```caddyfile
stellarlit.example.com {
    encode zstd gzip
    reverse_proxy 127.0.0.1:3000 {
        flush_interval -1
    }
}
```

```bash
sudo systemctl reload caddy
sudo journalctl -u caddy -f      # 看证书签发是否成功
```

`flush_interval -1` 表示不缓冲、来一段转一段,这是流式回答能逐字出现的关键。

### 方案 B:Nginx

```bash
sudo apt install -y nginx certbot python3-certbot-nginx
```

`/etc/nginx/sites-available/stellarlit`:

```nginx
# 80 只做跳转,顺便留给 certbot 验证
server {
    listen 80;
    server_name stellarlit.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name stellarlit.example.com;

    ssl_certificate     /etc/letsencrypt/live/stellarlit.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/stellarlit.example.com/privkey.pem;

    client_max_body_size 32m;          # 4 张 4MB 图片 base64 后约 22MB

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        # 覆盖而不是追加:限流读的是第一跳,追加会把客户端伪造的头留在最前面
        proxy_set_header X-Forwarded-For   $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection        "";

        proxy_buffering off;           # SSE 必须
        proxy_cache off;
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }
}
```

```bash
sudo ln -s /etc/nginx/sites-available/stellarlit /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d stellarlit.example.com
```

证书续期由 `certbot.timer` 自动处理,可用 `sudo certbot renew --dry-run` 验证。

> 如果 Nginx 前面还有 Cloudflare 等 CDN,`$remote_addr` 会变成 CDN 节点 IP,
> 所有用户共用一个限流桶。此时用 `ngx_http_realip_module` 信任 CDN 网段,
> 再改回 `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`。

### 方案 C:项目自带 nginx 容器(80/443 被其他站点占用)

服务器上已经有别的 nginx 占着 80/443,又不想改它的配置时,用项目自带的覆盖层:
nginx 只在容器内监听 443,宿主机映射到 `8443`,`proxy_pass` 走 Compose 内网到 `app:3000`。

**1. DNS**

在 `wenshi.xin` 下加一条 A 记录:主机记录 `stellarlit`,记录值 `39.105.213.187`。

**2. 签证书(不占用 80 端口,用 DNS-01)**

```bash
sudo mkdir -p /opt/stellarlit/certs
podman run --rm -it \
  -v /opt/stellarlit/certs:/etc/letsencrypt \
  certbot/certbot certonly --manual --preferred-challenges dns \
  -d stellarlit.wenshi.xin
```

按提示在阿里云 DNS 添加 TXT 记录 `_acme-challenge.stellarlit`,值为终端输出的字符串,
等一分钟再回车。证书会落在 `/opt/stellarlit/certs/live/stellarlit.wenshi.xin/`。

**3. 启动**

```bash
cd /root/stellarlit
echo 'TLS_DIR=/opt/stellarlit/certs' >> .env
echo 'NGINX_HTTPS_PORT=8443' >> .env
podman-compose -f compose.yaml -f compose.nginx.yaml up -d
```

用 Docker Compose 时把最后一条换成:

```bash
docker compose -f compose.yaml -f compose.nginx.yaml up -d
```

**4. 放行端口并验收**

安全组放行 `8443`,然后:

```bash
podman logs --tail 50 stellarlit-nginx-1
curl -I https://stellarlit.wenshi.xin:8443/
```

浏览器访问 `https://stellarlit.wenshi.xin:8443`。应用只需绑定回环地址:

```bash
sed -i 's/^APP_BIND=.*/APP_BIND=127.0.0.1/' .env
podman-compose -f compose.yaml -f compose.nginx.yaml up -d
```

nginx 通过 Compose 内网的 `app:3000` 访问应用,不依赖宿主端口。

**5. 如果以后能独占 80/443**

停掉占用端口的容器,把 `compose.nginx.yaml` 的映射改成 `80:80` 和 `443:443`,
就可以直接用 `https://stellarlit.wenshi.xin`。证书路径与配置不用改。

> DNS-01 手动签发的证书有效期 90 天,到期前需要重新执行一次。要自动续期,
> 改用 `acme.sh` 的阿里云 DNS API 模式,并把续期任务放进 cron。

### 两个头决定两件事

**`X-Forwarded-Proto` → 登录态。**
应用通过它判断请求是否 HTTPS,决定会话 Cookie 是否加 `Secure`。
TLS 在反代终止后,容器内部看到的是 http,所以这个头是唯一依据。

- 头缺失:Cookie 不带 `Secure`,能用但安全性下降。
- 头写死 `https` 而用户实际走 http:浏览器直接拒收 Cookie,表现为
  「登录成功又立刻掉线」。

**`X-Forwarded-For` → 限流。**
应用取这个头的第一跳作为客户端标识。缺失时所有人共用 `local` 一个桶,
一个人连续提问就会把全站限流。但它可以被客户端伪造,所以边缘反代必须
**覆盖**它,而不是把客户端传来的值原样保留在最前面。

### 改端口并验收

```bash
# .env
APP_BIND=127.0.0.1
```

```bash
docker compose up -d          # 端口变化会重建容器
curl -I https://stellarlit.example.com/
```

再在浏览器里确认三件事:

- 地址栏是锁,`http://` 会自动跳到 `https://`。
- DevTools → Application → Cookies,会话 Cookie 带 `Secure`。
- DevTools → Network,问答请求类型是 `eventsource`,回答逐段出现而不是最后一次性出现。

### 可选:安全响应头

确认站点正常后,可以再补 HSTS 等头。Caddy 写法:

```caddyfile
header {
    Strict-Transport-Security "max-age=31536000; includeSubDomains"
    X-Content-Type-Options "nosniff"
    Referrer-Policy "strict-origin-when-cross-origin"
}
```

先别急着加 `includeSubDomains`,等确认所有子域都上了 HTTPS 再加,否则回滚很麻烦。

## 六、日常运维

### 更新版本

```bash
cd stellarlit
git pull
docker compose up -d --build
docker compose logs -f app
```

镜像重建不会动 `postgres-data`、`redis-data` 两个命名卷和宿主的 `./data`。
数据库结构在启动时自动迁移,无需手工执行 SQL。

### 备份

三样东西必须一起备份,缺一不可:

```bash
# 1. 数据库
docker compose exec -T postgres pg_dump -U stellarlit stellarlit > backup-$(date +%F).sql

# 2. 媒体对象与磁盘缓存
tar czf data-$(date +%F).tgz data

# 3. .env(尤其 ENCRYPTION_KEY)
cp .env env-$(date +%F).bak
```

建议放进 cron 每天跑,并把备份同步到另一台机器或对象存储。只备份数据库
不备份 `ENCRYPTION_KEY`,恢复后所有厂商 API Key 都无法解密。

### 恢复

```bash
docker compose stop app
docker compose exec -T postgres psql -U stellarlit -d stellarlit < backup-2026-11-15.sql
tar xzf data-2026-11-15.tgz
docker compose start app
```

把备份的 `.env` 放回原位再启动,否则同样解不开密钥。

### 定时清理

服务启动时会跑一次清理,之后按 `MAINTENANCE_INTERVAL_MIN`(默认 360 分钟)重复:
清过期会话、淘汰图像分析缓存、按容量清理磁盘缓存、删除无引用的媒体孤儿对象。
也可以从外部触发:

```bash
curl -fsS -X POST https://stellarlit.example.com/api/maintenance/cleanup \
  -H "Authorization: Bearer $MAINTENANCE_TOKEN"
```

## 七、常见故障

| 现象 | 原因与处理 |
| :--- | :--- |
| 502 Bad Gateway | 容器没起来:`docker compose ps` / `logs app`;确认反代指向 `127.0.0.1:3000` 且 `APP_BIND` 一致。 |
| 登录成功但马上掉线 | 反代没传 `X-Forwarded-Proto`,Cookie 的 `Secure` 判断错了。 |
| 问答最后一次性吐出 | SSE 被缓冲:Nginx 加 `proxy_buffering off` 与 `X-Accel-Buffering no`,Caddy 加 `flush_interval -1`。 |
| 上传图片报 413 | `client_max_body_size` 太小,调到 `32m`。 |
| 一个人提问,所有人被限流 | 没传 `X-Forwarded-For`,所有请求都算 `local`。 |
| 构建被 killed | 内存不足,加 swap 或换 4G 机器。 |
| `Cannot find module './xxxx.js'` | 宿主机上同时跑了 dev 与 build,共用了 `.next`。本地不要边跑 dev 边 build;服务器只跑镜像。 |
| 问答提示未绑定模型 | 正常:去「设置 → 模型服务」绑定服务商并选择问答模型。 |
| MCP 调用 401 | MCP 令牌按账号签发,去「设置 → MCP 工具」生成,请求头带 `Authorization: Bearer <token>`。 |
